# Post-Quantum KMS: Signing and Verifying Documents with ML-DSA-87

## Overview

This example demonstrates how to use Google Cloud KMS with a post-quantum cryptographic key (ML-DSA-87) to sign a document and verify its signature, generating a `.sig` file.

ML-DSA-87 (Module Lattice Digital Signature Algorithm, security level 3) is a NIST-standardized post-quantum signature scheme designed to remain secure against attacks from future quantum computers.

## About Signature Verification and OpenSSL 3.5

Verifying ML-DSA-87 signatures requires **OpenSSL 3.5 or later**, as it is the first version to include native support for the NIST post-quantum signature algorithms.

If your operating system does not ship with OpenSSL 3.5+ (e.g. older Ubuntu versions), you can still run the verification using the provided **Docker image based on `alpine:latest`**, which already includes OpenSSL 3.5. The `verify.sh` script handles this automatically — no manual setup required.

## Prerequisites

- [Terraform](https://developer.hashicorp.com/terraform/install) >= 1.5.7
- [Google Cloud CLI (`gcloud`)](https://cloud.google.com/sdk/docs/install-sdk)
- [Docker](https://docs.docker.com/engine/install/) (used to run OpenSSL 3.5 via `alpine:latest` for signature verification)
- A Google Cloud project with billing enabled

> **Note:** Docker is required only for signature verification. If your system already has OpenSSL 3.5+ installed, the Docker image will still be used by `verify.sh` to ensure a consistent and reproducible environment across different operating systems.


## Authenticate with Google Cloud

1. Log in to your Google Cloud account.
    ```sh
    gcloud auth login
    ```

1. Set up Application Default Credentials, required by both Terraform and the scripts.
    ```sh
    gcloud auth application-default login
    ```

1. Set your project as the active project.
    ```sh
    gcloud config set project YOUR_PROJECT_ID
    ```

## Deploy the Infrastructure

1. Navigate to the bootstrap directory.
    ```sh
    cd 0-bootstrap
    ```

1. Copy the example tfvars file and fill in your values.
    ```sh
    cp terraform.example.tfvars terraform.tfvars
    ```

1. Edit `terraform.tfvars` and replace the placeholders with your values.
    ```hcl
    project_id   = "YOUR_PROJECT_ID"
    location     = "us-east1"
    keyring_name = "pqc-keyring"
    key_name     = "pqc-signing-key"
    ```

1. Initialize and apply Terraform.
    ```sh
    terraform init
    terraform apply
    ```

    > **Note:** Review the planned changes and type `yes` to confirm. Terraform will enable the Cloud KMS API, create the key ring, the ML-DSA-87 signing key, and grant the required IAM roles to your user.

1. Export the KMS key URI generated by Terraform. This variable is required by both scripts.
    ```sh
    export KMS_KEY_URI=$(terraform output -raw kms_key_uri)
    ```

## Download the Sample Document

1. Navigate to the bash-script directory.
    ```sh
    cd ../sign-verify
    ```

1. Download the RFC 5126 PDF, which will be used as the document to sign.
    ```sh
    curl -o sample.pdf https://pdfobject.com/pdf/sample.pdf
    ```

## Sign the Document

1. Make the script executable.
    ```sh
    chmod +x sign.sh
    ```

1. Run the sign script passing the PDF file as argument.
    ```sh
    ./sign.sh sample.pdf
    ```

    The expected output is:
    ```
    Signing file with ML-DSA-87 via GCP KMS...
      File     : sample.pdf
      Project  : YOUR_PROJECT_ID
      Location : us-east1
      Key Ring : pqc-keyring
      Key      : pqc-signing-key
      Version  : 1
      Output   : sample.sig

    Signature generated successfully!
      File : sample.sig
      Size : 4627 bytes (expected ~4627 bytes for ML-DSA-87)
    ```

    > **Note:** The `.sig` file contains the raw binary signature produced by the ML-DSA-87 key. Keep both the original document and the `.sig` file to perform verification.

## Verify the Signature

The verification requires **OpenSSL 3.5+**. The `verify.sh` script runs OpenSSL 3.5 inside a Docker container based on `alpine:latest`, which ships with OpenSSL 3.5 by default. This approach works on any operating system regardless of the locally installed OpenSSL version.

The Docker image is built automatically on the first run and reused on subsequent runs.

1. Make the script executable.
    ```sh
    chmod +x verify.sh
    ```

1. Run the verify script passing the original document.
    ```sh
    ./verify.sh sample.pdf
    ```

    Or explicitly passing both files:
    ```sh
    ./verify.sh sample.pdf sample.sig
    ```

    On the **first run**, the Docker image will be built automatically:
    ```
    Building Docker image (ml-dsa-verifier) with OpenSSL 3.5 (alpine:latest)...
    ```

    The expected output is:
    ```
    Verifying ML-DSA-87 signature...
      File      : sample.pdf
      Signature : sample.sig
      Project   : YOUR_PROJECT_ID
      Location  : us-east1
      Key Ring  : pqc-keyring
      Key       : pqc-signing-key
      Version   : 1

    Exporting public key from KMS...
      Public key saved to: /tmp/ml_dsa_verify_XXXXXX/pubkey.pem

    Verifying with OpenSSL 3.5 (alpine:latest Docker container)...
    Signature is VALID!
    ```

## Tamper Test (Optional)

This test confirms that the verification correctly rejects a document that has been modified after signing.

1. Append arbitrary content to the already-signed document to simulate tampering.
    ```sh
    echo "tampered" >> sample.pdf
    ```

1. Run the verify script against the modified document using the original signature.
    ```sh
    ./verify.sh sample.pdf sample.sig
    ```

    The expected output is:
    ```
    Verifying ML-DSA-87 signature...
    ...
    Verifying with OpenSSL 3.5 (alpine:latest Docker container)...
    Signature is INVALID!
    ```

    > **Note:** After the test, restore the original document by re-downloading it before running any further signing or verification steps.
    > ```sh
    > curl -o sample.pdf https://pdfobject.com/pdf/sample.pdf
    > ```

## Cleanup

1. Navigate to the bootstrap directory and destroy the infrastructure.
    ```sh
    cd ../0-bootstrap
    terraform destroy
    ```

    > **Note:** Review the planned destruction and type `yes` to confirm. This will schedule the KMS key version for destruction and delete the key ring. Make sure you no longer need the key before proceeding.
